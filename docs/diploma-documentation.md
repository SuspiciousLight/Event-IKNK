# Документация дипломного проекта

## 1. Краткое описание системы

Разрабатываемая система представляет собой VK Mini App для записи студентов на мероприятия образовательной организации. Приложение позволяет студентам просматривать список мероприятий, заполнять пошаговую форму регистрации, сохранять данные профиля для автоподстановки, отменять запись и устанавливать напоминания.

Для администратора предусмотрена отдельная панель управления: создание мероприятий, настройка регистрационных форм, сохранение шаблонов форм, просмотр зарегистрированных участников, выгрузка списка в Excel, запуск массовой in-app рассылки и просмотр журнала административных действий.

Ключевой особенностью проекта является учет требований по защите персональных данных: минимизация собираемых данных, явное согласие на обработку ПД, разграничение ролей, аудит чувствительных действий и запрет хранения секретов во frontend.

## 2. Актуальность темы

Организация студенческих мероприятий часто выполняется через разрозненные инструменты: чаты, таблицы, устные договоренности и внешние формы. Такой подход затрудняет контроль количества участников, ведет к дублированию записей, усложняет уведомление студентов и повышает риск некорректной обработки персональных данных.

VK Mini App является удобным форматом для студенческой аудитории, поскольку работает внутри привычной социальной платформы и не требует установки отдельного приложения. При этом backend-система позволяет централизованно хранить данные, контролировать права доступа и обеспечивать безопасность операций.

## 3. Объект, предмет и цель

Объект исследования: процесс записи студентов на мероприятия образовательной организации.

Предмет исследования: программная система автоматизации регистрации студентов на мероприятия с учетом требований к обработке персональных данных.

Цель проекта: разработать безопасное VK Mini App-приложение для просмотра мероприятий, регистрации студентов, управления формами записи и администрирования участников.

## 4. Задачи проекта

1. Проанализировать требования к системе регистрации студентов на мероприятия.
2. Спроектировать архитектуру frontend, backend и базы данных.
3. Реализовать backend API на NestJS с разграничением ролей и защитой данных.
4. Спроектировать и реализовать PostgreSQL-схему через Prisma ORM.
5. Реализовать frontend VK Mini App на React, TypeScript и VKUI.
6. Реализовать административные функции: формы, шаблоны, участники, экспорт и рассылки.
7. Провести security review и внедрить меры защиты персональных данных.

## 5. Обоснование выбора технологий

### React + TypeScript

React выбран для построения интерактивного пользовательского интерфейса с компонентной архитектурой. TypeScript снижает риск ошибок за счет статической типизации DTO, API-контрактов и frontend-состояния.

### VKUI и VK Bridge

VKUI обеспечивает визуальную совместимость с экосистемой VK Mini Apps, а VK Bridge используется для инициализации приложения и получения контекста запуска внутри VK.

### NestJS + TypeScript

NestJS выбран для backend-части из-за модульной архитектуры, поддержки dependency injection, guard/interceptor/filter-подхода и удобного разделения ответственности между controller и service слоями.

### PostgreSQL

PostgreSQL используется как надежная реляционная база данных с поддержкой транзакций, индексов, внешних ключей и строгой целостности данных. Это важно для регистраций, ограничений уникальности и истории согласий.

### Prisma

Prisma упрощает работу с базой данных, предоставляет типизированный клиент, миграции и снижает риск SQL injection за счет использования ORM-запросов вместо ручной сборки SQL.

### JWT в HttpOnly cookie

Для администратора используется JWT, передаваемый в `HttpOnly` cookie. Такой подход не требует хранения токена в `localStorage` или `sessionStorage`, что снижает риск кражи токена через XSS.

### ExcelJS

ExcelJS используется для выгрузки зарегистрированных участников в `.xlsx`. Формат удобен для административной работы и не требует передачи персональных данных во внешние сервисы в рамках MVP.

### Пользователь

2. Просмотр карточки мероприятия и активной формы регистрации.
3. Запись на мероприятие через пошаговую форму.
4. Сохранение профиля для автоподстановки: ФИО, телефон, email.
5. Принятие согласия на обработку персональных данных.
6. Просмотр собственных регистраций.
7. Отмена собственной регистрации.
8. Установка и отмена in-app напоминания о мероприятии.
9. Получение уведомлений об успешных и ошибочных действиях.

### Администратор

1. Авторизация через защищенный admin login.
2. Создание мероприятий.
3. Создание регистрационной формы для мероприятия.
4. Создание и переиспользование шаблонов форм.
5. Создание мероприятия на основе шаблона.
6. Просмотр зарегистрированных участников.
7. Фильтрация и пагинация списка регистраций.
8. Экспорт зарегистрированных участников в Excel.
9. Создание массовой in-app рассылки по участникам мероприятия.
10. Просмотр журнала административных действий.

## 7. Нефункциональные требования

1. Безопасность: backend должен проверять роли, права доступа и принадлежность данных пользователю.
2. Защита ПД: система должна хранить только данные, необходимые для регистрации на мероприятия.
3. Надежность: операции регистрации и сохранения ответов должны выполняться транзакционно.
4. Масштабируемость: архитектура должна позволять добавлять новые каналы уведомлений и внешние интеграции.
5. Поддерживаемость: проект должен быть разделен на независимые frontend/backend/shared пакеты.
6. Валидация: все входные данные должны проверяться на backend через DTO.
7. Наблюдаемость: действия администратора и ключевые пользовательские действия должны попадать в audit log.
8. Удобство: интерфейс должен быть понятен студенту и администратору без дополнительного обучения.

## 8. Описание архитектуры

Проект построен как `pnpm monorepo`:

```text
apps/
  frontend/     React + TypeScript + VKUI
  backend/      NestJS + Prisma + PostgreSQL
packages/
  shared/       Общие типы и DTO-контракты
prisma/
  schema.prisma Модель данных и связи
infra/
  docker-compose.yml PostgreSQL для локального запуска
```

Frontend отвечает за отображение интерфейса, маршрутизацию, работу с VK Bridge и вызовы backend API. Он не хранит секреты и не принимает решений о доступе к защищенным данным.

Backend является центром бизнес-логики и безопасности. Он валидирует DTO, проверяет роли, защищает endpoint через guards, выполняет транзакции через Prisma и пишет audit log.

PostgreSQL хранит пользователей, профили, мероприятия, формы, регистрации, ответы, согласия, напоминания, кампании рассылок и журнал действий.

## 9. Взаимодействие компонентов

```text
Студент / Администратор
        |
        v
VK Mini App frontend
        |
        | HTTPS + JSON API + cookie credentials
        v
NestJS backend API
        |
        | Prisma Client
        v
PostgreSQL
```

Основной поток регистрации:

```text
Пользователь открывает мероприятие
  -> frontend получает карточку и активную форму
  -> пользователь заполняет шаги формы
  -> frontend проверяет базовые ошибки ввода
  -> пользователь принимает согласие на ПД
  -> backend повторно валидирует все данные
  -> backend проверяет отсутствие активной повторной регистрации
  -> backend создает регистрацию, ответы и факт согласия
  -> пользователь видит итоговый экран
```

Основной поток администрирования:

```text
Администратор входит в систему
  -> backend выдает JWT в HttpOnly cookie
  -> администратор создает мероприятие и форму
  -> студенты регистрируются
  -> администратор просматривает список участников
  -> при необходимости запускает рассылку или выгружает Excel
  -> backend фиксирует действия в audit log
```

## 10. Описание базы данных

База данных спроектирована вокруг сущностей пользователя, мероприятия, формы регистрации и факта записи.

### Основные таблицы

`User` хранит системную учетную запись, роль, статус и связь с VK user id.

`UserProfile` хранит минимальный набор персональных данных для автоподстановки: ФИО, телефон и email.

`Admin` хранит учетную запись администратора, login, password hash и статус активности.

`Event` описывает мероприятие: название, описание, даты, место, вместимость и статус публикации.

`RegistrationForm` хранит форму регистрации конкретного мероприятия с версией и статусом.

`FormQuestion` хранит вопросы формы, их порядок, тип, обязательность и варианты ответов.

`FormTemplate` и `TemplateQuestion` позволяют сохранять шаблоны форм и переиспользовать их при создании новых мероприятий.

`EventRegistration` хранит факт записи пользователя на мероприятие, статус `ACTIVE` или `CANCELED`, дату отмены и причину.

`RegistrationAnswer` хранит ответы пользователя на вопросы формы.

`Consent` хранит факт согласия на обработку персональных данных: версию, hash текста, дату принятия и контекст мероприятия.

`Reminder` хранит in-app напоминания о мероприятии.

`NotificationCampaign` и `NotificationRecipient` описывают массовую рассылку и ее получателей.

`AuditLog` фиксирует действия пользователей и администраторов: actor, action, target type, target id, metadata и дату.

### Ограничения и индексы

1. Один пользователь имеет один активный профиль.
2. Администратор связан с одной системной учетной записью.
3. Версия формы уникальна в рамках мероприятия.
4. Вопросы формы уникальны по `position` и `fieldKey`.
5. Шаблон формы уникален по `templateCode` и `version`.
6. Активная регистрация пользователя на одно мероприятие ограничена уникальным ключом `eventId + userId + activeMarker`.
7. Согласие уникально по пользователю, типу, версии и контексту.
8. Для списков и фильтрации используются индексы по статусам, датам и внешним ключам.

## 11. Описание API

API разделено по модулям NestJS.

### Auth

`POST /api/v1/auth/admin/login` выполняет вход администратора и устанавливает JWT в `HttpOnly` cookie.

`POST /api/v1/auth/admin/logout` завершает admin-сессию и очищает cookie.

`GET /api/v1/auth/me` возвращает текущего пользователя по токену.

### Events

`GET /api/v1/events` возвращает список опубликованных мероприятий.

`GET /api/v1/events/:id` возвращает карточку мероприятия и активную опубликованную форму.

### Users

`GET /api/v1/users/me/profile` возвращает профиль автоподстановки текущего пользователя.

`PATCH /api/v1/users/me/profile` обновляет профиль текущего пользователя.

### Registrations

`GET /api/v1/registrations/me` возвращает список собственных регистраций.

`POST /api/v1/registrations` создает регистрацию на мероприятие.

`PATCH /api/v1/registrations/:registrationId/cancel` отменяет собственную регистрацию.

### Consents

`POST /api/v1/consents` сохраняет факт согласия на обработку ПД.

`GET /api/v1/consents/me` возвращает согласия текущего пользователя.

### Reminders

`GET /api/v1/reminders/registrations/:registrationId` получает напоминание по собственной регистрации.

`POST /api/v1/reminders/registrations/:registrationId` создает или обновляет напоминание.

`PATCH /api/v1/reminders/registrations/:registrationId/cancel` отменяет напоминание.

### Admin

`GET /api/v1/admin/events` возвращает список мероприятий для администратора.

`POST /api/v1/admin/events` создает мероприятие.

`POST /api/v1/admin/events/:eventId/forms` создает форму регистрации.

`GET /api/v1/admin/form-templates` возвращает шаблоны форм.

`POST /api/v1/admin/form-templates` создает шаблон формы.

`POST /api/v1/admin/events/from-template` создает мероприятие на основе шаблона.

`GET /api/v1/admin/events/:eventId/registrations` возвращает зарегистрированных участников.

`GET /api/v1/admin/events/:eventId/registrations/excel` выгружает участников в Excel.

`POST /api/v1/admin/events/:eventId/campaigns` создает in-app рассылку по участникам мероприятия.

`GET /api/v1/admin/audit-logs` возвращает журнал действий.

## 12. Пользовательские сценарии

### Просмотр мероприятий

Студент открывает приложение, видит список опубликованных мероприятий, краткое описание, дату и место проведения. При выборе мероприятия открывается карточка с подробной информацией.

### Регистрация на мероприятие

Пользователь открывает карточку мероприятия, переходит к форме регистрации, заполняет вопросы по шагам, подтверждает согласие на обработку персональных данных и отправляет форму. Backend проверяет ответы, профиль, согласие, вместимость и отсутствие активной повторной записи.

### Автоподстановка профиля

Пользователь может сохранить ФИО, телефон и email в профиле. При следующих регистрациях эти данные используются для автоподстановки, что уменьшает количество ручного ввода.

### Отмена записи

Пользователь открывает раздел «Мои записи» и отменяет активную регистрацию. Запись не удаляется физически, а получает статус `CANCELED`; также отменяются активные напоминания.

### Напоминание

Пользователь выбирает время напоминания до начала мероприятия. Система сохраняет in-app напоминание, которое может быть отменено пользователем.

### Администрирование

Администратор входит в панель управления, создает мероприятие, настраивает форму регистрации или использует шаблон, просматривает участников, выгружает Excel и запускает in-app рассылку только по активным зарегистрированным участникам.

## 13. Меры защиты персональных данных

1. Минимизация данных: хранятся только ФИО, телефон, email и ответы, необходимые для регистрации.
2. Целевое использование: персональные данные используются только для записи на мероприятия.
3. Явное согласие: факт согласия хранит версию текста, hash текста и дату принятия.
4. Разграничение ролей: пользователь и администратор имеют разные права доступа.
5. Backend authorization: права проверяются на backend, frontend-гейты используются только для удобства интерфейса.
6. Защита от IDOR/BOLA: пользовательские операции фильтруются по `userId` из auth context.
7. Защита admin token: JWT хранится в `HttpOnly` cookie, не в `localStorage`.
8. CSRF-защита: cookie-auth state-changing запросы проверяют trusted origin и специальный header.
9. Rate limiting: чувствительные endpoint ограничены по количеству запросов.
10. Audit logging: входы администратора, экспорт, рассылки, регистрации, отмены, согласия и изменения профиля журналируются.
11. Безопасные логи: в request logs не записываются тела запросов и сырые персональные данные.
12. Ограниченный экспорт: Excel содержит только необходимые поля, без служебных идентификаторов и внутренних metadata.
13. Soft delete: регистрации и связанные процессы поддерживают мягкое удаление и отмену без потери истории.

## 14. Преимущества системы

1. Интеграция с привычной для студентов платформой VK.
2. Единый процесс регистрации, отмены и уведомлений.
3. Гибкие пошаговые формы с шаблонами для повторного использования.
4. Административная панель без необходимости вести отдельные таблицы вручную.
5. Security-first подход к персональным данным и действиям администратора.

## 15. Ограничения MVP

1. Напоминания и рассылки реализованы только как in-app контур.
2. Экспорт реализован в Excel, без прямой интеграции с Google Sheets.
3. Rate limiting реализован in-memory и рассчитан на один backend instance.
4. Нет полноценной очереди фоновых задач для рассылок и напоминаний.

## 16. Инструкция по запуску

1. Установить зависимости:

```bash
corepack pnpm install
```

2. Запустить PostgreSQL:

```bash
docker compose -f infra/docker-compose.yml up -d
```

3. Создать `.env` на основе `.env.example` и заполнить значения:

```text
DATABASE_URL
JWT_SECRET
ADMIN_LOGIN
ADMIN_PASSWORD
CORS_ORIGIN
CSRF_TRUSTED_ORIGINS
```

4. Сгенерировать Prisma Client:

```bash
corepack pnpm exec prisma generate --schema prisma/schema.prisma
```

5. Применить миграции:

```bash
corepack pnpm --filter backend exec prisma migrate dev --schema ../../prisma/schema.prisma
```

6. Создать seed-администратора:

```bash
corepack pnpm --filter backend exec prisma db seed --schema ../../prisma/schema.prisma
```

7. Запустить frontend и backend:

```bash
corepack pnpm dev
```

Архитектура разделяет frontend, backend и базу данных, что упрощает развитие проекта. Особое внимание уделено защите персональных данных: система минимизирует сбор информации, фиксирует согласие, ограничивает доступ по ролям и журналирует чувствительные действия.

MVP не претендует на полный промышленный контур, однако содержит production-like основу, на базе которой можно развивать интеграции, фоновые задачи, расширенную аналитику и дополнительные механизмы безопасности.
